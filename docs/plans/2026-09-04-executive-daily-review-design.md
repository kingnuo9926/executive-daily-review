## 1. 产品概述

### 1.1 要解决什么问题
企业高管日常工作高密度、强决策，但极少系统复盘：
- 复盘价值高，但**写**门槛高、耗时长，难以坚持；
- 零散笔记无法沉淀，更无法跨日/跨周期看出趋势；
- 普通日记缺引导，容易变成流水账，反思深度不够。

### 1.2 产品定位
**AI 教练式语音日记**。高管用几分钟、以"说话"的方式，在 AI 教练的全双工语音引导下完成对当天关键事的回顾、反思、洞察与行动规划；系统自动转写并结构化沉淀；未来可自动聚合为周/月/季复盘报告。

### 1.3 价值三角
- **降低门槛**：语音输入，动口不动手，通勤/睡前即可完成。
- **保证质量**：教练式引导 + 四段式主线，避免流水账，提升反思深度。
- **释放洞察**：结构化数据 + 周期聚合，把"日记"升级为"成长资产"。

### 1.4 目标用户
大中型企业的中高层管理者（CEO/VP/BU 负责人/区域总）。对隐私敏感、时间稀缺、有自我精进与团队领导诉求。

## 2. 核心体验与对话设计

### 2.1 一次日复盘的结构（四段式 + 自适应）
每次会话约 4 步主线，AI 在每步内**按需追问**，整体像一次轻量教练对话。

| 阶段 | 主线问题（AI 发起） | 引导目的 | 自适应追问示例 |
| --- | --- | --- | --- |
| ① 关键事 | "今天最关键的 1–3 件事是什么？" | 聚焦，避免流水账 | "其中哪件最消耗你？""这件事里你是主导还是被动？" |
| ② 想法/感受 | "当时你是怎么判断的？情绪和能量如何？" | 还原决策情境与状态 | "那个判断你后来有没有动摇？""当时压力大吗？" |
| ③ 洞察/遗憾 | "哪些做得好？若重来会不同？学到了什么？" | 提炼洞察与模式 | "这和你上周说的'授权不够'有关吗？""这个坑以后怎么避开？" |
| ④ 下一步 | "明天/近期最该做的 1 件事是什么？" | 形成可行动项 | "这件事最晚什么时候做？""需要谁配合？" |

### 2.2 自适应机制（让对话"懂你"）
- **用户画像驱动**：基于行业、角色、历史高频主题（如"决策犹豫""团队授权"），让追问更贴身。
- **模式识别**：跨日检测到反复出现的卡点/情绪，主动在合适节点点出（"这好像是你这周第二次提到……"）。
- **主线回归**：当高管跑题过远，AI 以温和方式拉回当前阶段，保证一次复盘有闭合感。
- **长度自适应**：识别到高管疲惫/简短时自动收敛，不强行追问。

### 2.3 示例对话（节选）
> AI：今天最关键的 1–3 件事是什么？
> 高管：下午和 XX 客户谈崩了，还有早上定了 Q4 的预算。
> AI：先说谈崩的那件——当时你是怎么判断对方会接受的？
> 高管：我以为价格不是问题，结果他们卡在交付周期。
> AI：所以真正的卡点是交付节奏，不是价格。若重来，你会先确认哪一点？
> ……（进入③洞察 → ④下一步，AI 提炼出行动项"明日与交付负责人对齐周期"）

## 3. 全双工语音架构

### 3.1 体验目标
像一通电话：高管随时可插话打断 AI，AI 能自然停顿、等待、接话；不要求"你说完我才能说"。

### 3.2 技术组合（国内合规、密钥自持）
| 能力 | 候选方案 | 说明 |
| --- | --- | --- |
| 实时 ASR（语音转写） | 讯飞开放平台 / 火山引擎 | 中文识别准、支持实时流式 |
| 大模型（流式推理+打断） | 通义千问 / 智谱 GLM / DeepSeek（企业 API） | 负责教练式追问与摘要 |
| 实时 TTS（语音合成） | 火山引擎 / 讯飞 | 自然度高的中文语音 |
| 端点/打断检测 | VAD（语音活动检测） | 判断何时"听"、何时"说" |

> 备选：评估 OpenAI Realtime API 一体化方案（语音自然度最佳），但数据出境需谨慎，与"自有服务器"策略冲突，默认不采用，除非后续另行决策。

### 3.3 对话状态机（三态切换）
```
        ┌─────────┐  检测到人声   ┌─────────┐
        │  SPEAKING │ <────────── │  LISTEN  │
        │ (AI 说)  │             │ (听高管) │
        └─────────┘ ──────────> └─────────┘
              │ 说完+等待          │ 端点静音
              ▼                   ▼
        ┌─────────┐           ┌─────────┐
        │  THINKING│ <──────── │ (转写完成)│
        │ (推理)  │ ─────────> │          │
        └─────────┘ 生成回复    └─────────┘
```
- **LISTEN**：录音→ASR 流式转写，VAD 检测插话即中断 SPEAKING。
- **THINKING**：将累计文本送大模型，流式生成回复。
- **SPEAKING**：TTS 流式播报；检测到人声立即切回 LISTEN（打断）。

### 3.4 延迟预算（目标）
- 端到端首字响应 < 800ms（VAD+ASR 部分结果 → 大模型首 token → TTS 首包）。
- 打断响应 < 300ms（停止 TTS、切回聆听）。

## 4. 技术栈与系统架构

### 4.1 总体架构
```
┌─────────────────────────┐
│  移动端 App (RN/Flutter) │  录音/播放、会话 UI、本地草稿
└───────────┬─────────────┘
            │ HTTPS / WSS（实时音频流）
┌───────────▼─────────────┐
│  自有后端服务            │  鉴权、会话编排、状态机、
│  (Node/Python + 云)     │  调用 ASR/LLM/TTS、存储
└─────┬──────────┬────────┘
      │          │
┌─────▼───┐  ┌───▼──────────┐  ┌──────────────┐
│ 自有数据库│  │ 企业级大模型 │  │ 实时语音服务 │
│PostgreSQL│  │ /语音 API    │  │ (ASR/TTS)    │
└─────────┘  └──────────────┘  └──────────────┘
```
- **客户端**：React Native（推荐，生态成熟、语音/原生桥接方便）或 Flutter。
- **后端**：自有服务器，负责任务编排与三方调用聚合，密钥仅存服务端。
- **存储**：PostgreSQL（关系型，便于聚合查询），敏感字段加密；音频对象存自有对象存储。
- **隐私**：原文与密钥均在自有服务端，端到端不落第三方；传输全程 TLS。

### 4.2 关键后端模块
- 会话服务：管理一次复盘的生命周期与状态机。
- 语音网关：对接 ASR/TTS，处理流式双向音频（WSS）。
- 教练引擎：基于主线 + 用户画像生成追问（Prompt 编排 + 上下文管理）。
- 沉淀服务：转写文本 → 结构化字段/标签抽取 → 入库。
- 聚合服务：周期报告生成 + 历史语音检索问答。

## 5. 数据模型（为聚合而设计）

### 5.1 实体关系
- **User**（高管）：id、行业、角色、画像标签、偏好。
- **ReviewSession**（一次日复盘）：id、userId、date、durationSec、energyScore(1–5)、overallMood、audioRef、status。
- **Segment**（四段之一）：sessionId、stage(1–4)、transcript(文本)、audioRef、summary。
- **Tag**（衍生标签）：sessionId、type(主题/情绪/卡点/行动)、value。
- **ActionItem**（行动项）：sessionId、content、dueDate、done(bool)、followUpSessionId。
- **Report**（周期报告）：userId、periodType(周/月/季)、range、content、highlights。

### 5.2 为聚合预留的字段
- 情绪能量值、关键词标签（主题/情绪极性/卡点类型）
- 行动项及截止、完成状态（用于"行动完成率"）
- 跨日主题共现（用于"反复出现的卡点"）

### 5.3 聚合逻辑（高层级回顾）
- **周报**：本周关键主题词云、情绪/能量走势曲线、未完成行动清单、AI 一句总结。
- **月报**：主题演化（环比）、高频卡点 Top3、成长信号、与上月对比。
- **季报**：阶段画像、能力维度曲线（决策/情绪/人际/战略）、下一季聚焦建议。
- **语音追问历史**：高管可问"上个月我在团队授权上进展如何？"→ 检索历史片段 + 大模型作答。

## 6. MVP 与路线图

### 6.1 MVP（先验证对话体验，控制范围）
- 单端先行（建议先 Android 或 Web 壳），跑通主链路；
- 四段式对话 + 半结构化自适应；
- 语音：MVP 阶段可先用**轮流对话**降低复杂度，验证教练逻辑后再升级全双工；
- 自有后端 + 本地/自有库存储；
- 基础**周报**聚合作为高层级回顾的最小验证。

### 6.2 路线图（分阶段）
1. **MVP**：四段式 + 语音（轮流→全双工）+ 周报。
2. **语音打磨**：全双工打断/停顿/自然度优化。
3. **聚合深化**：月报、季报、主题画像。
4. **智能追问**：跨日模式识别、个性化教练。
5. **多端发布**：iOS+Android 上架、团队协作/教练后台（可选）。

### 6.3 验证指标
- **21 天日活留存**：高管能否养成习惯（最核心）。
- 单次复盘时长（目标 3–8 分钟）。
- 结构化完整度（四段均有内容 + 至少 1 个行动项）。
- 周报打开率与"有用"反馈率。

## 7. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 高管难以坚持（留存低） | 极简启动、语音优先、可断点续聊、温和提醒不骚扰 |
| 语音识别不准（口音/环境噪声） | 选高准中文 ASR、端点检测、关键字段文本确认 |
| 隐私/合规顾虑 | 自有服务器、加密存储、明确授权与数据归属 |
| 全双工体验不自然（打断/延迟） | MVP 先用轮流，逐步升级；严格延迟预算 |
| 大模型"追问空洞" | 教练 Prompt 工程 + 用户画像 + 历史上下文 |
| API 成本 | 缓存、摘要替代全文、按需调用 |

## 8. 待定决策（需后续确认）
1. **AI/语音具体厂商**：ASR/LLM/TTS 最终选型与商务（国内合规优先）。
2. **MVP 落地的具体端**：先 Android 还是先 Web 壳验证。
3. **是否私有化部署大模型**：合规等级与成本权衡。
4. **教练 Persona 语气**：严肃/温暖/锐利？是否允许"挑战式"追问。
5. **是否含多人/团队维度**：当前仅个人；未来是否给上级/教练看聚合。
